# 持续改进机制

Skill的自我进化系统。核心原则：**用户反馈是改进的唯一驱动力。**

---

## 改进循环

```
用户反馈 → 理解意图 → 提炼规则 → 写入文件 → 下次生效
     ↑                                    │
     └────────────────────────────────────┘
```

没有用户反馈，就不改。不凭AI猜测去"优化"。

---

## 规则生命周期

每条规则从用户反馈中诞生，经历生命周期：

```
用户反馈(案例) → 经验提炼(lessons-learned) → 规范固化(design-spec) → 定期验证
```

### 升级条件

| 阶段 | 位置 | 触发条件 |
|------|------|----------|
| 案例级 | lessons-learned 反馈表 | 用户首次提出 |
| 经验级 | lessons-learned 布局经验/技术陷阱 | 同类问题出现2次 |
| 规范级 | design-spec | 同类问题出现3次，或用户明确要求 |

### 淘汰条件

- PptxGenJS版本更新导致workaround不再需要
- 规则与更新后的规则矛盾
- 连续10次生成未触发且无用户反馈相关

---

## 定期整理

**每5次使用后执行一次，确保经验库健康：**

1. **反馈消化检查**：反馈表中所有条目是否都已提炼为可执行规则？
2. **升级检查**：是否有同类反馈3次以上但未升级为规范？
3. **去重检查**：lessons-learned 和 design-spec 是否有重复？重复则保留spec，精简learned
4. **过时检查**：是否有规则已不再适用？

整理结果记录在 usage-log.md。

---

## 知识去重

随着经验积累，lessons-learned和design-spec会出现重复：

1. **同一规则在两处都有** → 保留design-spec中的精确版本，lessons-learned中只留简要引用
2. **lessons-learned超过300行** → 精简：已升级为design-spec的案例保留在反馈表，从布局经验中删除
3. **design-spec超过400行** → 考虑拆分（color-spec.md, layout-spec.md）

---

## 效果衡量

| 指标 | 衡量方法 | 目标 |
|------|----------|------|
| 质检轮数 | 每次生成需要几轮修复 | ≤2轮 |
| 用户负面反馈率 | 负面反馈次数/总使用次数 | 逐次降低 |
| 反馈消化率 | 已提炼为规则的反馈/总反馈 | 100% |
| 新问题率 | 每次生成发现的新类型问题数 | 递减趋势 |
