# PPTX 创建技能

根据主题或大纲，创建专业、视觉独特的幻灯片。

## 工作流程

智能体根据当前状态自主决定路径，没有固定流水线——跳到任何合理的步骤即可。

```
0. 读取经验 → 1. 理解需求 → 2. 选择主题 → 3. 选择路线 → 4. 生成 → 5. 质检 → 6. 积累经验
```

### 进度反馈（必须执行）

**PPT生成是耗时操作，用户等待时没有任何反馈体验很差。** 在每个耗时步骤开始前，向用户发送简短的进度更新。

#### 反馈时机

| 步骤 | 反馈内容 | 示例 |
|------|----------|------|
| 读取经验库 | — | 不需要，瞬间完成 |
| 理解需求 | 确认理解 | "📝 收到，我来梳理需求..." |
| 选择主题 | 展示选项或确认 | "🎨 选用海洋渐变主题（深蓝+蓝绿）" |
| 生成大纲 | 展示结构 | "📋 大纲完成：封面→3个章节→结尾，共16页" |
| 开始生成 | 告知开始 | "⚙️ 开始生成PPT，预计需要1-2分钟..." |
| 生成完成 | 告知进度 | "✅ PPT生成完成，正在质检..." |
| 质检中 | 告知进度 | "🔍 逐页视觉检查中..." |
| 质检发现问题 | 通知修复 | "🔧 发现X处问题，正在修复..." |
| 全部完成 | 最终交付 | "✅ 全部完成！共16页，附优化摘要" |

#### 反馈原则

1. **每个耗时>10秒的步骤都要反馈**：生成脚本执行、PDF转换、图片渲染、质检
2. **反馈要简短**：1-2句话，不要写长篇说明
3. **用emoji标记状态**：📝 🎨 📋 ⚙️ ✅ 🔍 🔧，视觉上快速区分
4. **不要重复反馈相同状态**：如果还在生成中，不要每隔几秒发一次"仍在生成"
5. **质检发现问题时要具体**："第8页文字溢出"而非"发现一些问题"
6. **最终交付时附摘要**：改了什么、最终效果如何

### 第0步：读取经验库

**在开始任何工作之前**，读取 `references/lessons-learned.md`。这个文件记录了从实际使用中积累的技术陷阱、布局经验、对比度规则和用户反馈。避免重复犯错比修复错误更高效。

### 第1步：理解需求

明确以下信息：
- 主题和目的
- 目标受众
- 大致页数
- 风格偏好（正式/轻松/大胆/极简）
- 是否有已有内容需要整合（文字、数据、图片）

如果用户提供了大纲或已有内容，直接跳到第3步。

### 第2步：选择主题

向用户展示 `assets/themes/` 中的可用主题。每个主题包含名称、配色方案和字体搭配，让用户选择一个。如果没有合适的，生成自定义主题。

展示主题时，读取 `assets/themes/` 中的每个 `.md` 文件，呈现：
- 主题名称
- 配色方案（含十六进制色值）
- 字体搭配
- 适用场景

如果用户想要不同的风格，按相同格式创建自定义主题并保存到 `assets/themes/`。

### 第3步：选择路线

**模板路线** — 当 `assets/templates/` 中有合适的 .pptx 模板时使用：
1. 扫描 `assets/templates/` 寻找匹配
2. 使用 pptx 技能的编辑流程：缩略图 → 解包 → 编辑内容 → 清理 → 打包
3. 读取 `references/pptx-quick-ref.md` 了解编辑脚本

**HTML路线** — 当没有合适模板，或用户想要自定义设计时使用：
1. 生成大纲（结构 + 每页要点）
2. 用所选主题的配色/字体将每页渲染为 HTML
3. 向用户展示 HTML 进行视觉确认
4. 使用 `scripts/html_to_pptx.js` 将 HTML 转换为 .pptx
5. 读取 `references/layout-patterns.md` 了解布局选项

智能体自主决定走哪条路线。除非有明确的模板匹配，默认走 HTML 路线。

### 第4步：生成

**开始生成前，向用户发送进度反馈。**

#### HTML 路线：

1. **创建大纲** — 确定幻灯片结构，为每页分配布局模式（L1-L8）
2. **→ 反馈**：展示大纲结构（章节+页数+布局分配）
3. **渲染 HTML 幻灯片** — 每页一个 HTML 文件，使用主题的 CSS 变量
4. **预览** — 向用户展示 HTML，征求反馈
5. **转换** — 运行 `node scripts/html_to_pptx.js input.html output.pptx`
6. **→ 反馈**："⚙️ 正在转换为PPTX..."
7. **迭代** — 修复问题，重新转换

#### PptxGenJS 直接生成路线：

1. **创建大纲** — 确定幻灯片结构，为每页分配布局模式
2. **→ 反馈**：展示大纲结构
3. **编写生成脚本** — 完整的 .js 文件
4. **→ 反馈**："⚙️ 开始生成PPT，预计1-2分钟..."
5. **执行脚本** — `node script.js`
6. **→ 反馈**："✅ PPT生成完成，正在质检..."
7. **迭代** — 修复问题，重新执行

#### 模板路线：

1. **分析模板** — `python -m markitdown template.pptx` + `python scripts/thumbnail.py template.pptx`
2. **内容映射** — 将大纲各部分匹配到模板布局
3. **填充内容** — 解包、编辑 XML、清理、打包（使用 pptx 技能的脚本）
4. **迭代** — 修复问题

### 第5步：质检（必须执行）

**假设一定存在问题。你的任务是找到它们。**

**质检开始前，向用户发送进度反馈。**

1. **→ 反馈**："🔍 逐页视觉检查中..."

2. 转换为图片进行视觉检查：
   ```bash
   python scripts/office/soffice.py --headless --convert-to pdf output.pptx
   pdftoppm -jpeg -r 150 output.pdf slide
   ```

3. 逐页检查：
   - 元素重叠
   - 文字溢出或被截断
   - 对比度不足（浅色文字在浅色背景上，深色在深色上）
   - 间距不均或对齐偏移
   - 内容缺失或占位符文字未替换
   - 连续页面使用相同布局
   - 标题下方的装饰线（AI 生成的标志——删掉它）

4. **如发现问题 → 反馈**："🔧 发现X处问题（第X页YYY、第X页ZZZ），正在修复..."

5. 修复问题并重新验证。至少完成一轮修复-验证循环且无新问题后，才能宣布完成。

6. **→ 反馈**："✅ 质检通过！" + 最终交付摘要

### 第6步：积累经验

**每次生成完成后必须执行。核心原则：用户反馈是改进的唯一驱动力。**

#### 6.1 主动询问反馈

生成交付后，主动询问用户：
- "效果怎么样？有什么需要调整的？"
- 如果用户提出修改意见 → 这是改进的来源，按6.2处理
- 如果用户表示满意 → 记录"无负面反馈"，跳过6.2

#### 6.2 处理用户反馈

**用户反馈必须被消化为可执行规则，不能只记不用。**

```
用户反馈 → 理解真实意图 → 提炼为可执行规则 → 写入参考文件 → 记录到反馈表
```

**理解真实意图**：用户说的往往是表象，要挖到根因
- "这里不好看" → 为什么？对比度？间距？层级？
- "太挤了" → 间距规则需要调整
- "看不清" → 对比度/字号规则需要调整

**提炼为可执行规则**：每条反馈必须转化为下次生成时可直接执行的规则
- ❌ "用户不喜欢平淡" → 无法执行
- ✅ "标题栏用浅色底+彩色字；核心指标大号右对齐" → 可执行
- ❌ "绿色不够醒目" → 无法执行
- ✅ "绿色文字用#2E7D32（非#27AE60），背景用#C8E6C9（非#E8F8E8）" → 可执行

**写入参考文件**：根据反馈类型写入对应位置

| 反馈类型 | 写入位置 | 示例 |
|---------|---------|------|
| 风格偏好 | lessons-learned > 用户风格偏好 | "不要小清新，要强对比" |
| 技术问题 | lessons-learned > PptxGenJS技术陷阱 | "行级颜色不生效，用单元格级" |
| 版式/间距 | design-spec > 排版细节 | "卡片高度按内容量计算" |
| 色彩/对比度 | design-spec > 色彩体系 | "绿色文字用#2E7D32" |
| 组件/布局 | design-spec > 组件库 | "时间轴加箭头方向感" |

**记录到反馈表**：在 lessons-learned.md 用户反馈表中追加
- 格式：日期 | 场景 | 反馈原文 | 改进措施 | 归档位置
- **反馈原文保留用户原话**
- **归档位置写明写入了哪个文件的哪条规则**

#### 6.3 反馈升级

**同类用户反馈出现3次以上**，说明是稳定的设计规律，升级处理：
- 从 lessons-learned 的具体案例 → 提升为 design-spec 的通用规则
- 例如：3次反馈"卡片底部留白过多" → 升级为 design-spec 中的卡片高度计算表

#### 6.4 使用记录

**每次生成完成后，在 `references/usage-log.md` 中追加一行。**

#### 6.5 定期整理

**每5次使用后，执行一次整理：**
- 检查反馈表中所有条目是否都已提炼为规则（不能只记不改）
- 检查是否有同类反馈3次以上但未升级
- 检查 lessons-learned 和 design-spec 是否有重复（重复则保留spec，精简learned）
- 检查是否有规则过时（API变更、不再适用）

整理结果记录在 usage-log.md 的健康检查列。

## 设计规范

无论选择哪条路线，以下规范都必须遵守。

### 配色

- **为这个主题选颜色。** 如果配色方案适用于任何随机演示文稿，说明不够具体。
- **一个主色**（60-70% 视觉权重），1-2 个辅助色，一个锐利的强调色。
- **深浅三明治结构：** 标题页+结尾页用深色背景，内容页用浅色背景。或者全程深色营造高级感。
- **绝不默认蓝色。** 主题配色应反映内容主题。

### 布局

- **每页必须有视觉元素** — 图片、图表、图标或形状。禁止纯文字页。
- **布局必须变化。** 不要在连续页面重复同一布局。
- **正文左对齐。** 只有标题居中。
- **字号对比要明显：** 标题 36-44pt，正文 14-16pt。如果看起来差不多，层级就错了。

### 视觉签名

选择一个标志性元素，在每页重复出现：
- 圆角图片框
- 彩色圆圈中的图标
- 单侧粗边框
- 统一的卡片风格

这创造了一致性而非单调。

### 字体

选择有特色的字体搭配——不要默认 Arial。每个主题指定了标题+正文字体组合。

| 元素 | 字号 |
|------|------|
| 幻灯片标题 | 36-44pt 粗体 |
| 章节标题 | 20-24pt 粗体 |
| 正文 | 14-16pt |
| 注释 | 10-12pt 弱化色 |

### 间距

- 最小边距 0.5 英寸
- 内容块之间 0.3-0.5 英寸
- 留白——不要填满每一寸空间

### 禁忌

- 连续页面使用相同布局
- 正文居中对齐
- 标题下方的装饰线（AI 标志）
- 默认蓝色配色方案
- 纯文字页面
- 低对比度元素
- 连续文本混排（易换行断裂，用子卡片代替）

> 💡 更多从实际使用中总结的禁忌和经验，见 `references/lessons-learned.md`

## 参考文件

- `references/improvement-loop.md` — **持续改进机制**。改进循环（被动/主动/定期）、规则生命周期（案例→经验→规范）、知识去重、使用计数、效果衡量。**每5次使用后读取**执行健康检查。
- `references/usage-log.md` — **使用记录**。每次生成后追加一行，用于触发定期健康检查。
- `references/design-spec.md` — **设计规范**。色彩体系（语义色/色板扩展/深色背景色阶）、版式规范（页面结构/卡片/信息层级）、组件库（指标卡/风险卡/时间轴/策略卡/表格）、排版细节（字号/对齐/间距/装饰）、图表配色、禁忌清单。**生成时参照**确保专业度。
- `references/lessons-learned.md` — **经验库**。从实际使用中积累的技术陷阱、布局经验、对比度规则、用户反馈。**生成前必须读取**，避免重复犯错。每次收到用户反馈后，将改进经验追加到该文件。
- `references/pptx-quick-ref.md` — PptxGenJS API 速查和常见坑。用代码生成 .pptx 时读取。
- `references/layout-patterns.md` — 8 种布局模式，含 HTML 模板和 PptxGenJS 对应代码。选择布局时读取。
- `assets/themes/` — 主题定义（配色方案 + 字体搭配）。用户选择主题时读取。
- `assets/templates/` — 按类别组织的 .pptx 模板文件。考虑模板路线时扫描。

## 依赖

- `npm install -g pptxgenjs` — 从零创建 .pptx
- `pip install "markitdown[pptx]"` — 从 .pptx 提取文本
- LibreOffice (`soffice`) — 质检时转 PDF
- Poppler (`pdftoppm`) — 质检时 PDF 转图片
